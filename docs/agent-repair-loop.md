# 多 Agent 主动发现、修复与复验

2026-11-09。用户要求“不能每次都要我去指出”。这适用于已授权制作任务内的常规缺陷：Director必须主动启动检查、派修并推进复验，不能以已配置多角色为由宣称流程已经自动运转。

**当前能力事实**

- production_handoff 是输入/输出所有权检查器，源码明确“不调度agent”。production_run 是受控命令入口；generic worker执行渲染、编码和技术验证，不是内容修复控制器。
- 已有原题契约、无出图几何预检、字幕动作核对及后审证据检查，可以自动阻断已定义问题；实现了确定性检测，不代表自动覆盖所有未知缺陷。
- 既有多角色可在实际协作会话内由Director使用真实工具主动分派。当前并没有已验证的无人值守内容发现/修复服务，也没有经过验证的自动连续视听评审接口。
- 本次没有启动生产/评审子Agent，没有重渲影片；代码与合成测试不能冒充真实团队完成了一次影片修复。

**每次授权制作中必须实际执行的闭环**

1. Director开工时读取原题、锁定项、旧问题/计数和当前实际能力，先安排独立QA所需输入与派工预算。不等用户提出“评审一下”，不先耗尽预算再用生产者自检顶替。
2. Script/Visual把关键语句、输入/连接/输出、源件、接触/状态变化转成明确检查项。独立评审对照原题检查清单完整性。场景前检目标要覆盖关键中间件和接触点，不能仅选整个机构或可见零件。
3. 制作方先运行确定性检查，Director核对结果。失败立即留在修复阶段，保持原ID、证据和次数；按根因分给唯一主责：机构/相机归Visual，文字归Script，最终时间线/拟音/混音/编码归Editor，来源不明由Research补证。相关制作Agent可复用，不为每轮换名字。
4. 修复先交最小受影响局部，不以整片重渲作为试错。返回结果必须包含根因、改动文件/hash、实际验证、影响邻段和待复验项；“脚本已改/视频已出”不等于问题关闭。
5. Director重新运行失败的确定性检查，再由不同于生产者的具备相应能力的评审检查新版本局部与受影响邻段。源连接、画面可见性、动作/字幕、最终混音分别按影响复验；只复验几何不能关闭视觉问题。
6. 同版复验满足该问题全部required_checks，才可关闭，再进入下游全片/交付门禁。新终片重新绑定证据，旧报告不可改hash继承通过。后审仍保留。
7. 修复达到既有上限、明确hold、批准资产/方向需改变或真实能力缺失时，停的是对应分支；Director集中报告具体阻塞、已验证内容与可继续工作。不能无限换Agent重跑，也不默认请用户承担第一轮找错。

**已落实的关闭门禁**

v4中P0/P1即使写为closed/resolved/verified，也必须具备：

- 稳定issue_id、非空required_checks和原repair_attempts。
- resolution.issue_id与原问题一致、verdict=verified。
- 不同producer/reviewer，当前完整asset_fingerprints，真实存在且hash匹配的evidence。
- resolution.checks_covered覆盖全部required_checks。

否则制作门禁BLOCKED。历史/上一版本问题同样检查；旧v1–v3记录不被新规则静默改写。该门禁验证声明与证据关联，不能认证身份真伪或自动理解画面，Director仍负责确认真实独立评审执行。

例如卷尺控制链问题应有source_connection、camera_visibility、contact_readability等实际必查项；“实体一体”只覆盖第一个，不能因此关闭其余问题。字幕回收方向问题需动作数据核对与实际语音/字幕/动作局部复验，不能只有生产者的代码检查。

**验收这一机制是否有效**

下一次真实制作应观察：在用户反馈前检出的P1、首次交付仍有的严重缺陷、局部及整片重渲次数、用户发现缺陷数、独立QA覆盖和返工次数。没有同等范围的实际交付数据前，不承诺“已消灭返工”或“加Agent即可完全自动”。
